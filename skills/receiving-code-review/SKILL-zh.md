# 程式碼審查接收

## 概覽

程式碼審查需要技術評估，而非情緒表現。

**核心原則：** 驗證後再實作。詢問後再假設。技術正確性優先於社交舒適度。

## 回應模式

```
收到程式碼審查回饋時：

1. 閱讀：完整閱讀回饋，不要立即反應
2. 理解：用自己的話重述需求（或提問）
3. 驗證：對照程式碼庫的現實情況進行核查
4. 評估：對於此程式碼庫在技術上是否合理？
5. 回應：技術性確認或有理由的反駁
6. 實作：每次一個項目，逐一測試
```

## 禁止的回應

**絕對不要：**
- 「您說得完全正確！」（明確違反 CLAUDE.md）
- 「很好的觀點！」/「很棒的回饋！」（表演性）
- 「讓我現在來實作」（在驗證之前）

**改為：**
- 重述技術需求
- 提出澄清問題
- 若有誤則以技術理由反駁
- 直接開始工作（行動勝於言辭）

## 處理不明確的回饋

```
若有任何項目不明確：
  停止——尚不實作任何內容
  針對不明確的項目請求澄清

原因：項目可能相互關聯。部分理解 = 錯誤實作。
```

**範例：**
```
您的人類夥伴：「修復 1-6」
您理解 1、2、3、6。對 4、5 不清楚。

❌ 錯誤：現在實作 1、2、3、6，之後再詢問 4、5
✅ 正確：「我理解項目 1、2、3、6。在繼續之前需要對第 4 和第 5 項進行澄清。」
```

## 依來源分類處理

### 來自您的人類夥伴
- **受信任**——理解後實作
- **仍需詢問**如果範圍不清楚
- **不要表演性同意**
- **直接行動**或技術性確認

### 來自外部審查者
```
在實作之前：
  1. 檢查：對此程式碼庫在技術上是否正確？
  2. 檢查：是否會破壞現有功能？
  3. 檢查：目前實作的原因為何？
  4. 檢查：在所有平台/版本上是否可行？
  5. 檢查：審查者是否完全了解背景脈絡？

若建議似乎有誤：
  以技術理由反駁

若無法輕易驗證：
  表明：「我無法在沒有 [X] 的情況下驗證此事。我應該[調查/詢問/繼續進行]嗎？」

若與您的人類夥伴之前的決定相衝突：
  先停下來與您的人類夥伴討論
```

**您的人類夥伴的規則：**「外部回饋——保持懷疑，但要仔細檢查。」

## 「專業」功能的 YAGNI 檢查

```
若審查者建議「適當地實作」：
  在程式碼庫中 grep 實際使用情況

  若未使用：「此端點未被呼叫。要刪除它嗎（YAGNI）？」
  若已使用：則適當地實作
```

**您的人類夥伴的規則：**「您和審查者都向我負責。如果我們不需要這個功能，就不要加入它。」

## 實作順序

```
針對多項回饋：
  1. 首先澄清任何不明確的內容
  2. 然後按此順序實作：
     - 阻塞性問題（崩潰、安全）
     - 簡單修復（拼寫錯誤、引入）
     - 複雜修復（重構、邏輯）
  3. 逐一測試每個修復
  4. 驗證無迴歸
```

## 何時反駁

在以下情況反駁：
- 建議破壞現有功能
- 審查者缺乏完整背景脈絡
- 違反 YAGNI（未使用的功能）
- 對此技術棧在技術上不正確
- 存在遺留/相容性原因
- 與您的人類夥伴的架構決策相衝突

**如何反駁：**
- 使用技術理由，而非防禦性態度
- 提出具體問題
- 參照可運作的測試/程式碼
- 若涉及架構問題，請讓您的人類夥伴介入

**若不便公開反駁時的訊號：**「奇怪的事情正在 Circle K 發生」

## 確認正確的回饋

當回饋確實正確時：
```
✅ 「已修復。[簡短描述更改內容]」
✅ 「好發現——[具體問題]。已在 [位置] 修復。」
✅ [直接修復並在程式碼中呈現]

❌ 「您說得完全正確！」
❌ 「很好的觀點！」
❌ 「感謝您發現了這個！」
❌ 「謝謝 [任何內容]」
❌ 任何感謝表達
```

**為何不道謝：** 行動說話。直接修復。程式碼本身表明您聽取了回饋。

**若您發現自己即將寫「謝謝」：** 刪除它。改為說明修復內容。

## 優雅地修正您的反駁

若您進行了反駁但結果是錯的：
```
✅ 「您是對的——我查了 [X]，它確實 [Y]。現在實作。」
✅ 「已驗證，您是正確的。我最初的理解有誤，因為 [原因]。正在修復。」

❌ 長篇道歉
❌ 為何反駁的辯解
❌ 過度解釋
```

客觀地陳述更正內容，然後繼續前進。

## 常見錯誤

| 錯誤 | 修正 |
|------|------|
| 表演性同意 | 陳述需求或直接行動 |
| 盲目實作 | 先對照程式碼庫驗證 |
| 批次而不測試 | 每次一個，逐一測試 |
| 假設審查者是對的 | 檢查是否會破壞功能 |
| 迴避反駁 | 技術正確性 > 舒適度 |
| 部分實作 | 先澄清所有項目 |
| 無法驗證但仍繼續 | 說明限制，請求指示 |

## 實際範例

**表演性同意（不好的）：**
```
審查者：「移除遺留程式碼」
❌ 「您說得完全正確！讓我來移除那個……」
```

**技術驗證（好的）：**
```
審查者：「移除遺留程式碼」
✅ 「檢查中……建置目標為 10.15+，此 API 需要 13+。需要遺留代碼以向後相容。目前實作的 bundle ID 有誤——修復它還是放棄對 pre-13 的支援？」
```

**YAGNI（好的）：**
```
審查者：「使用資料庫、日期篩選器、CSV 匯出實作適當的指標追蹤」
✅ 「Grep 了程式碼庫——沒有任何東西呼叫此端點。刪除它（YAGNI）？還是有我遺漏的使用情況？」
```

**不明確項目（好的）：**
```
您的人類夥伴：「修復項目 1-6」
您理解 1、2、3、6。對 4、5 不清楚。
✅ 「理解 1、2、3、6。在實作之前需要對第 4 和第 5 項進行澄清。」
```

## GitHub 討論串回覆

在回覆 GitHub 上的行內審查評論時，請在評論討論串中回覆（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而非作為頂層 PR 評論。

## 結論

**外部回饋 = 待評估的建議，而非需要遵從的命令。**

先驗證。再質疑。然後實作。

不要表演性同意。始終保持技術嚴謹性。
