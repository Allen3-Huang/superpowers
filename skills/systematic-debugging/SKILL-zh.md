# 系統化除錯

## 概述

隨機修復浪費時間並製造新的錯誤。快速補丁掩蓋了潛在問題。

**核心原則：** 在嘗試修復之前，始終找到根本原因。修復症狀就是失敗。

**違反此流程的字面意義，就是違反除錯的精神。**

## 鐵律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

如果你尚未完成第一階段，你就不能提出修復方案。

## 使用時機

適用於任何技術問題：
- 測試失敗
- 生產環境中的錯誤
- 意外行為
- 效能問題
- 建置失敗
- 整合問題

**尤其在以下情況使用：**
- 面臨時間壓力（緊急情況讓猜測顯得很誘人）
- 「只需一個快速修復」似乎顯而易見
- 你已經嘗試了多個修復方案
- 之前的修復無效
- 你對問題沒有完全理解

**不要在以下情況跳過：**
- 問題看起來很簡單（簡單的錯誤也有根本原因）
- 你很趕（急忙只會保證需要返工）
- 主管要求立即修復（系統化比折騰更快）

## 四個階段

在進入下一個階段之前，你必須完成每個階段。

### 第一階段：根本原因調查

**在嘗試任何修復之前：**

1. **仔細閱讀錯誤訊息**
   - 不要略過錯誤或警告
   - 它們通常包含確切的解決方案
   - 完整閱讀堆疊追蹤
   - 記錄行號、檔案路徑、錯誤代碼

2. **穩定重現**
   - 你能可靠地觸發它嗎？
   - 確切的步驟是什麼？
   - 每次都會發生嗎？
   - 如果無法重現 → 收集更多資料，不要猜測

3. **檢查最近的變更**
   - 什麼變更可能導致這個問題？
   - Git diff、最近的提交
   - 新的相依套件、設定變更
   - 環境差異

4. **在多元件系統中收集證據**

   **當系統有多個元件時（CI → 建置 → 簽署、API → 服務 → 資料庫）：**

   **在提出修復方案之前，新增診斷工具：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **範例（多層系統）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **這能揭示：** 哪個層級失敗（密鑰 → 工作流程 ✓，工作流程 → 建置 ✗）

5. **追蹤資料流**

   **當錯誤深藏於呼叫堆疊時：**

   完整的反向追蹤技術請參閱此目錄中的 `root-cause-tracing.md`。

   **快速版本：**
   - 錯誤值從哪裡產生？
   - 是什麼用錯誤值呼叫了這個？
   - 持續向上追蹤直到找到來源
   - 在來源處修復，而非在症狀處修復

### 第二階段：模式分析

**在修復之前找到模式：**

1. **找到有效範例**
   - 在同一個程式碼庫中找到類似的有效程式碼
   - 什麼有效的東西與損壞的東西相似？

2. **與參考資料比較**
   - 如果在實作模式，完整閱讀參考實作
   - 不要略讀——讀每一行
   - 在應用之前完全理解模式

3. **識別差異**
   - 有效的和損壞的之間有什麼不同？
   - 列出每個差異，無論多小
   - 不要假設「那不可能有影響」

4. **理解相依性**
   - 這需要哪些其他元件？
   - 需要什麼設定、配置、環境？
   - 它有什麼假設？

### 第三階段：假設與測試

**科學方法：**

1. **形成單一假設**
   - 清楚地說明：「我認為 X 是根本原因，因為 Y」
   - 寫下來
   - 要具體，不要模糊

2. **最小化測試**
   - 進行最小可能的變更來測試假設
   - 每次一個變數
   - 不要同時修復多個問題

3. **繼續之前先驗證**
   - 有效了嗎？是 → 第四階段
   - 無效？形成新假設
   - 不要疊加更多修復

4. **當你不知道時**
   - 說「我不理解 X」
   - 不要假裝知道
   - 尋求幫助
   - 進一步研究

### 第四階段：實作

**修復根本原因，而非症狀：**

1. **建立失敗的測試案例**
   - 最簡單可能的重現
   - 盡可能使用自動化測試
   - 如果沒有框架，使用一次性測試腳本
   - 修復之前必須有此測試
   - 使用 `superpowers:test-driven-development` 技能撰寫適當的失敗測試

2. **實作單一修復**
   - 解決已識別的根本原因
   - 每次一個變更
   - 不要「順便」改進
   - 不要捆綁重構

3. **驗證修復**
   - 測試現在通過了嗎？
   - 沒有其他測試損壞嗎？
   - 問題確實解決了嗎？

4. **如果修復無效**
   - 停止
   - 計數：你嘗試了多少個修復？
   - 如果 < 3：返回第一階段，用新資訊重新分析
   - **如果 ≥ 3：停止並質疑架構（以下步驟 5）**
   - 不要在未進行架構討論的情況下嘗試第 4 個修復

5. **如果 3 個以上修復失敗：質疑架構**

   **指示架構問題的模式：**
   - 每個修復揭示不同位置的新共享狀態/耦合/問題
   - 修復需要「大規模重構」才能實作
   - 每個修復在其他地方製造新症狀

   **停止並質疑基本原則：**
   - 這個模式從根本上是合理的嗎？
   - 我們是否「出於純粹的慣性而堅持它」？
   - 我們應該重構架構，而非繼續修復症狀嗎？

   **在嘗試更多修復之前與你的人類夥伴討論**

   這不是一個失敗的假設——這是一個錯誤的架構。

## 紅旗——停止並遵循流程

如果你發現自己在想：
- 「先快速修復，稍後再調查」
- 「就試著改變 X，看看是否有效」
- 「新增多個變更，執行測試」
- 「跳過測試，我會手動驗證」
- 「大概是 X，讓我修復那個」
- 「我不完全理解，但這可能有效」
- 「模式說 X，但我會以不同方式調整它」
- 「以下是主要問題：[在未調查的情況下列出修復方案]」
- 在追蹤資料流之前提出解決方案
- **「再試一次修復」（當已嘗試 2 次以上時）**
- **每個修復揭示不同位置的新問題**

**所有這些都意味著：停止。返回第一階段。**

**如果 3 個以上修復失敗：** 質疑架構（參見第四階段第 5 步）

## 您的人類夥伴提示您做錯了的信號

**注意這些重新導向：**
- 「那沒有發生嗎？」- 你在未驗證的情況下假設了
- 「它會告訴我們...嗎？」- 你應該新增證據收集
- 「停止猜測」- 你在未理解的情況下提出修復方案
- 「深思熟慮這個」- 質疑基本原則，而非只是症狀
- 「我們卡住了嗎？」（沮喪）- 你的方法無效

**當你看到這些時：** 停止。返回第一階段。

## 常見的合理化藉口

| 藉口 | 現實 |
|--------|---------|
| 「問題很簡單，不需要流程」 | 簡單的問題也有根本原因。對於簡單的錯誤，流程很快。 |
| 「緊急情況，沒時間走流程」 | 系統化除錯比猜測-檢查式折騰**更快**。 |
| 「先試試這個，再調查」 | 第一個修復設定了模式。從一開始就做對。 |
| 「確認修復有效後再寫測試」 | 未測試的修復無法持久。先測試才能證明。 |
| 「同時修復多個問題節省時間」 | 無法隔離有效的部分。會導致新的錯誤。 |
| 「參考文件太長，我會調整模式」 | 不完整的理解必然導致錯誤。完整閱讀它。 |
| 「我看到問題了，讓我修復它」 | 看到症狀 ≠ 理解根本原因。 |
| 「再試一次修復」（2 次以上失敗後） | 3 次以上失敗 = 架構問題。質疑模式，不要再修復。 |

## 快速參考

| 階段 | 主要活動 | 成功標準 |
|-------|---------------|------------------|
| **1. 根本原因** | 讀取錯誤、重現、檢查變更、收集證據 | 理解「是什麼」和「為什麼」 |
| **2. 模式** | 找到有效範例、進行比較 | 識別差異 |
| **3. 假設** | 形成理論、最小化測試 | 已確認或形成新假設 |
| **4. 實作** | 建立測試、修復、驗證 | 錯誤已解決，測試通過 |

## 當流程揭示「沒有根本原因」時

如果系統化調查揭示問題確實是環境性的、時序相依的或外部的：

1. 你已完成流程
2. 記錄你調查的內容
3. 實作適當的處理（重試、逾時、錯誤訊息）
4. 新增監控/日誌記錄供未來調查

**但是：** 95% 的「沒有根本原因」案例是調查不完整。

## 實際影響

從除錯過程中：
- 系統化方法：15-30 分鐘修復
- 隨機修復方法：2-3 小時折騰
- 首次修復成功率：95% vs 40%
- 引入的新錯誤：幾乎為零 vs 常見
