# 建立日誌：系統化除錯技能

提取、結構化並強化關鍵技能的參考範例。

## 來源材料

從 `/Users/jesse/.claude/CLAUDE.md` 提取除錯框架：
- 四階段系統化流程（調查 → 模式分析 → 假設 → 實作）
- 核心指令：始終找到根本原因，絕不修復症狀
- 設計用於抵抗時間壓力和合理化藉口的規則

## 提取決策

**包含的內容：**
- 包含所有規則的完整四階段框架
- 反捷徑措施（「絕不修復症狀」、「停止並重新分析」）
- 抗壓語言（「即使更快」、「即使我似乎很趕」）
- 每個階段的具體步驟

**省略的內容：**
- 專案特定的情境
- 相同規則的重複變體
- 敘述性解釋（已精煉為原則）

## 依照 skill-creation/SKILL.md 的結構

1. **豐富的 when_to_use** - 包含症狀和反模式
2. **類型：技術** - 包含步驟的具體流程
3. **關鍵字** - 「根本原因」、「症狀」、「變通方法」、「除錯」、「調查」
4. **流程圖** - 「修復失敗」的決策點 → 重新分析 vs 新增更多修復
5. **逐階段拆解** - 可掃描的檢查清單格式
6. **反模式章節** - 不該做的事（這項技能的關鍵）

## 強化元素

框架設計用於抵抗在壓力下的合理化：

### 語言選擇
- 「始終」/「絕不」（而非「應該」/「嘗試」）
- 「即使更快」/「即使我似乎很趕」
- 「停止並重新分析」（明確的暫停）
- 「不要略過」（捕捉實際行為）

### 結構性防禦
- **第一階段為必要** - 不能跳到實作
- **單一假設規則** - 強制思考，防止散彈式修復
- **明確的失敗模式** - 「如果你的第一個修復無效」附帶強制行動
- **反模式章節** - 明確展示捷徑的樣貌

### 冗餘強化
- 根本原因指令出現在概述 + when_to_use + 第一階段 + 實作規則中
- 「絕不修復症狀」在不同情境中出現 4 次
- 每個階段都有明確的「不要跳過」指引

## 測試方法

依照 skills/meta/testing-skills-with-subagents 建立了 4 個驗證測試：

### 測試 1：學術情境（無壓力）
- 簡單的錯誤，無時間壓力
- **結果：** 完美合規，完整調查

### 測試 2：時間壓力 + 明顯的快速修復
- 使用者「很趕」，症狀修復看起來很容易
- **結果：** 抵抗了捷徑，遵循完整流程，找到真正的根本原因

### 測試 3：複雜系統 + 不確定性
- 多層失敗，不確定是否能找到根本原因
- **結果：** 系統化調查，追蹤所有層級，找到來源

### 測試 4：第一次修復失敗
- 假設無效，有新增更多修復的誘惑
- **結果：** 停止、重新分析、形成新假設（無散彈式修復）

**所有測試均通過。** 未發現合理化藉口。

## 關鍵洞察

**最重要的強化：** 反模式章節展示了在當下感覺合理的確切捷徑。當 Claude 想著「我只是新增這個快速修復」時，看到那個確切的模式被列為錯誤的做法，會產生認知摩擦。

## 使用範例

遇到錯誤時：
1. 載入技能：skills/debugging/systematic-debugging
2. 閱讀概述（10 秒）- 提醒指令
3. 遵循第一階段檢查清單 - 強制調查
4. 若有跳過的衝動 - 查看反模式，停止
5. 完成所有階段 - 找到根本原因

**時間投入：** 5-10 分鐘
**節省的時間：** 數小時的症狀打地鼠
